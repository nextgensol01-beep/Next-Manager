# Email delivery review workspace

Current asynchronous acceptance, dashboard activity/history and skipped-reason grouping are documented in [browser-coordinated delivery](email-browser-delivery.md). These supersede historical synchronous completion notes below.

The existing tracker “Email clients” modal has a preparation view and a delivery-review workspace. The subsequent [Email Delivery Protection implementation](email-delivery-protection.md) adds server-enforced authorization, verified approval email, optional Send PIN, draft confirmation, Hold to Send, audit and safe campaign retries. It supersedes the earlier confirmation-only delivery behavior described in the historical visual-refinement notes below.

Preparation shows a glass workflow selector, Initial/Reminder segmented control, the actual selected-row scope and an explicit “Preview eligible clients” action. Context changes invalidate the preview without starting requests. The same preview action becomes the processing capsule. Reminder copy follows the two actual awaited operations: checking reply status, then preparing recipients. No percentage or fabricated stage is shown.

Processing uses four independently circulating color bodies in a locally scoped glass treatment: violet, blue, cyan and a small pink accent. Normal-speed captures were reviewed in light and dark mode. Motion is removed under reduced-motion preferences while static color and the loading message remain. Global AI variables, shared glass defaults, workflow stepper, toggles and handoff components were not changed; source hashes were compared with the pre-change snapshot.

Review condenses context into a campaign bar. The audience navigator has Eligible/Skipped controls, immediate local company/client-ID search and category matching when already supplied by loaded tracker rows. Clicking a client changes inspection only. It never includes or excludes clients. Compact rows show recipient counts and issues derived from the same validation now used by the final action. Skipped clients show the server’s actual reason, with no recipient editor.

Only the inspected eligible client mounts a recipient editor and email iframe, including with 500 prepared clients. To/CC/Not included assignments remain mutually exclusive. “Add another recipient” adds a single-address row with To/CC selection and a remove action, up to five additional recipients per client. The button stays visible and disables at five; removing a row frees a slot. New rows receive focus, and removal returns focus to Add. Rows, including unfinished entries, remain keyed by tracker entry while navigating clients. Blank rows are ignored in delivery; populated rows must contain one valid email address. The row editor synchronizes the existing additional To/CC address lists, preserving the delivery payload and normalization path. Refresh replaces drafts according to the original preparation behavior.

The inline iframe uses the original `srcDoc` and Gmail signature insertion path. Subject and attachment filenames are retained. Expand opens the existing full preview, restores focus on close and leaves the workspace open. The desktop panes scroll independently beneath a fixed header/campaign/footer. Smaller widths use the audience/detail view with “Back to audience.” Radio controls and audience rows support keyboard navigation. Keyboard-initiated preparation moves focus to the mounted Audience heading; pointer preparation does not move it there.

Send remains the primary action, Gmail drafts secondary. Both open the single authorization sheet using a frozen normalized payload. Drafts default to explicit confirmation; direct sends require the configured server-authoritative identity checks and deliberate hold. Validation, attachments, completion/error toasts and the daily cap remain, with exact campaign binding and safer retry handling.

## Cursor-reactive Send material

Send follows the existing `LiquidNavControl` in `components/client-trackers/WorkflowStepNavigation.tsx` and its `.workflow-nav-*` styles. Only Send was modified; neither the reference stepper nor the shared material/pointer utilities changed. Local normalized pointer coordinates come from the actual button rectangle. `useMotionValue`, `useSpring` (stiffness 190, damping 28 for a response without overshoot) and `useTransform` drive magnetic translation and optical coordinates without React state updates on pointer moves. The reference stepper wakes on direct pointer entry; Send uses that same entry model.

The shell is clamped to 3px horizontally and 2px vertically. Cyan travels over X 26–74% and Y 22–78% during pointer interaction. Blue follows at a smaller amplitude, while violet moves in the opposite direction. The localized specular reflection follows X and Y while staying near the top surface. The plane uses the same spring coordinates, advancing up to 2.4px/.9px with a tiny local cyan reflection behind it. A separate spring blends resting composition into pointer response and returns it smoothly on leave. Press reduces magnetic displacement, compresses the shell toward .978 and concentrates the color bodies using the same press MotionValue; release recovers through the spring. The base is brighter, more translucent saturated blue, and the depth layers avoid an almost-black center. All material remains clipped inside the existing pill.

Reduced motion and disabled states stop magnetic and optical travel. Reduced motion keeps a static bright transmission composition and focus/press feedback. A 48-second seamless phase drives small independent cyan, blue, violet and specular harmonics at rest. Pointer activation progressively removes that idle bias, so it cannot fight cursor position. The loop pauses in hidden tabs and is stopped/reset when disabled or reduced motion is active. The existing count, disabled conditions, confirmation callback and delivery pipeline remain unchanged.

Browser verification covers left/right and up/down color coordinates, opposing parallax, specular travel, circular corner traversal, rapid corner changes with spring trailing, physical limits and smooth leave recovery in both themes. It also repeats pointer/Space/Enter confirmation, disabled/reduced-motion and existing draft/send/500-client checks.
