# Client Tracker email delivery protection

Settings → Email & Delivery (`/dashboard/settings?tab=email-delivery`) manages one organization-wide policy. Server defaults are defined once in `lib/email-delivery-security.ts`: drafts require confirmation; direct sends require Email OTP followed by a 1.1-second hold; OTP lasts five minutes, has a 45-second resend cooldown, and locks after five attempts. Direct-send batches of 50 or more require fresh Email OTP, including when the ordinary policy uses Send PIN. Audit logging cannot be disabled.

## Setup

1. Set two independent, cryptographically random server environment secrets, each at least 32 bytes: `EMAIL_DELIVERY_OTP_SECRET` and `EMAIL_SEND_PIN_PEPPER`. Generate them with your deployment secret manager or, locally, `node -e "console.log(require('node:crypto').randomBytes(48).toString('base64'))"` separately for each variable. Store values privately in the server environment and restart the app. `.env.example` contains blank placeholders only; existing `.env` values were not inspected or modified.
2. Keep the existing MongoDB, admin authentication and `GMAIL_*` OAuth configuration. The Gmail setup link opens the existing `/dashboard/gmail-setup` flow. Verification codes use that Gmail account.
3. Open Email & Delivery and choose **Set up approval email**. The configured admin email may be suggested but becomes trusted only after its own OTP succeeds. Default direct sending stays locked until a trusted approval email and the OTP secret are present.
4. Set a dedicated six-digit Send PIN if choosing PIN protection. The PIN is separate from the login password. PIN-protected operations stay locked if no PIN or server pepper exists.

Changing a trusted approval email requires authorization through the current trusted address (or current PIN when no trusted address exists), then verification of the new address. Changing/removing an existing PIN and changing policy require the current trusted OTP, with current PIN as the fallback. Initial configuration still requires an administrator session. Generic policy PATCH rejects email replacement, PIN values and unknown fields.

**Restrict duplicate email addresses** in Settings → Email & Delivery → Delivery protection defaults to on, including for existing settings documents. When enabled, a normalized address cannot appear across multiple clients in a new batch, whether in To or CC. Turn it off and save the verified settings change to allow a shared contact to receive each client's separate email. The server enforces the setting both when requesting authorization and when starting delivery; the control applies to sends and drafts. Duplicate client entries and duplicate To/CC addresses within one client message still fail validation. Existing authorized campaigns preserve their exact snapshot and safe retry behavior after policy changes.

Missing or undersized secrets produce an actionable configuration error and deny the protected operation. Rotating the OTP secret invalidates pending codes; rotating the PIN pepper requires replacing existing PIN hashes through the authorized setup flow. Preserve existing secrets across deploys. No plaintext code, PIN, hash, pepper or server secret is returned through public APIs or stored in browser persistence.

## Server boundary and data

Every new API, and the existing tracker delivery endpoint, checks `getServerSession(authOptions)` and `isAdminSession`. Missing sessions receive 401; non-admins receive 403. Mutation handlers reject cross-site browser requests and validate bounded bodies. The frontend's `confirmed: true` provides draft confirmation only; it never authorizes a fresh direct send.

`EmailDeliverySecuritySettings` stores public policy, version, verified trusted email and a private PIN hash. `EmailDeliveryApproval` stores owner, purpose, tracker/workflow/campaign/kind/mode, exact batch SHA-256, policy version, required and verified factors, attempts, expiry and consumption. OTP generation uses `crypto.randomInt`; storage is HMAC-SHA256 of approval ID and code, compared with `timingSafeEqual`. PIN material is first HMACed with the server pepper, then bcrypt-hashed with cost 12, avoiding bcrypt's input-length limit. [Node crypto documentation](https://nodejs.org/api/crypto.html#cryptotimingsafeequala-b) describes the underlying comparison primitive.

`EmailDeliverySecurityGate` stores atomic rolling rate windows and the organization delivery lease. OTP sends have destination/user cooldowns, 10 requests per user per hour, and 100 per organization per hour; approval creation permits 30 per user per ten minutes; PIN verification permits ten per user per 15 minutes. Per-challenge attempt counters and locks are persisted. Resending replaces the hash and expiry, invalidating the old code without resetting attempts. Closing a modal clears input state; abandoned challenges expire.

`securityDatabase()` waits for model initialization and required unique/TTL indexes before authorization. Approval IDs, campaign IDs and gate keys are unique. Approval cleanup occurs seven days after creation, while authorization expiry is enforced immediately in application queries. Gate cleanup uses TTL; security audits have separate persistent retention. Existing campaigns gain optional authorization metadata and item delivery/history fields; no destructive migration or backfill runs. Databases must support MongoDB aggregation-pipeline updates (MongoDB 4.2+). Conditional updates reserve rate slots, consume approval and claim items atomically. See [MongoDB's single-document atomicity documentation](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/).

The shared canonicalizer includes tracker, workflow, campaign, kind, mode, each entry/client and company name, normalized sorted To/CC, exact subject/HTML, and sorted attachment document IDs. Message ordering is deterministic. The client uses the same representation for invalidation; only the server computes the authoritative hash. Approval request, verification and delivery use the same immutable prepared snapshot. Recipient/message/attachment/context changes discard the operation and require fresh approval. Blank editor rows and equivalent address normalization do not create a different delivery.

Delivery consumes a matching, unexpired, verified approval before campaign creation/binding. An organization lease serializes client campaigns and durable per-item claims prevent duplicates even if a worker's lease expires during Gmail I/O. A crash between approval consumption and campaign binding can recover only that same owner and exact operation. Replaying approval for a new campaign, changing mode, or using another user's campaign fails.

Already-authorized campaigns resume from stored items under the same owner/tracker/workflow/kind/mode/hash without another OTP. Legacy campaigns require authorization before gaining metadata, and their stored item content must match. Client-side network failures retain the campaign and snapshot; retries consult server state. The same valid operation can recover after a network interruption; material changes generate a new campaign.

Gmail acknowledgment is stored before history/activity bookkeeping. A retry recovers missing EmailLog records without re-sending. Pending recipients alone are submitted. Unknown Gmail network/5xx outcomes are marked uncertain and blocked from automatic retries or new deliveries for that client/workflow. Review Gmail and the recorded campaign outcome before resolving an ambiguous result; the app does not guess that a failed HTTP response means Gmail sent nothing. A worker crash can leave a claimed item similarly uncertain. Existing initial/reminder/reply/seven-day/eligibility/attachment rules remain enforced, including stored successful campaign results when history writing was interrupted.

The 350-client-send rolling 24-hour cap and 350ms serial pause remain. Outstanding claims and ambiguous outcomes reserve quota; successful sends awaiting history also reserve quota conservatively. Recovery can briefly overcount a delivery already in history until its history marker is saved; it cannot increase the allowance. Security OTP emails are separate from client campaign quotas. A quota-paused unchanged campaign resumes without reauthorization, while a newly prepared campaign requires its own approval.

`EmailDeliverySecurityAudit` records safe settings changes, OTP/PIN/approval transitions, failed operations, delivery authorization/start/outcomes, identity, IP and user agent. Completion records contain requested/completed/failed/pending/uncertain counts and status. The admin-only activity endpoint returns cursor-paginated safe fields; it does not expose secrets, recipient lists, message HTML, IP or user agent to the Settings feed.

## Interface and verification

Email & Delivery uses explicit, verified saves for normal policy controls. A persistent header shows Saved, Unsaved changes, Saving or Couldn’t save; changed rows carry a small pending dot. A sticky bar in the settings content column counts changed fields, offers Discard and Save changes, and briefly confirms successful persistence. The existing protected review/OTP-or-PIN step still runs before PATCH; Saving is shown during the actual write, never as a substitute for verification. Only a successful authoritative server response updates the saved baseline and draft. Failed responses/network failures retain the draft and a persistent retry; retry fetches the current server version and rebases only user-edited fields. Normal controls freeze while their save is reviewed/in flight, preventing newer edits from being mistaken for saved values. PIN/approval-email flows remain independent and rebase identity updates without overwriting pending normal settings.

The Settings shell shares one policy draft between its desktop and mobile panels, so responsive resizing and protected-flow completion do not discard edits. Leaving through Settings tabs, the mobile Settings back action, or ordinary internal links while dirty offers Keep editing, Discard changes or Save & continue. Save & continue navigates only after successful verified persistence, including after a failed attempt and explicit retry. Hard refresh/close uses beforeunload only while dirty. There is no global router/history monkeypatch; native SPA history transitions outside these controls are not intercepted, and drafts remain available while the Settings shell stays mounted. No secrets or PIN/OTP values are stored by this save-state model.

The existing Email clients workspace and animated Send material remain. One authorization sheet replaces the former send confirmation. Draft confirmation explicitly says “Nothing will be sent.” OTP and PIN use one native input behind six visual cells, numeric entry/paste/autofill and masked PINs. Factor verification proceeds to the deliberate hold; ordinary clicks, early release, pointer exit/cancellation, blur and hidden tabs do not send. Space/Enter holds work, focus is trapped and returned, countdowns are not announced every second, and reduced-motion preferences remove processing travel. Processing effects and styles are scoped to this feature.

The authorization sheet shows its vivid capsule only while preparation or factor verification is running, then resolves to a compact Identity verified status. Hold to Send retains the 1,100ms safety timer. Its local liquid material uses the existing independently moving violet/blue/cyan bodies, revealed through an elapsed-time clip mask with a gently curved edge; requestAnimationFrame updates the mask without React renders per frame. Early release drains over 240ms and preserves approval. Only a completed hold starts delivery: the same control becomes an indeterminate Sending state, then briefly acknowledges the server-confirmed completed count before the sheets close. Recoverable errors restore that control without discarding campaign/approval state; partial, quota-paused and uncertain outcomes retain their existing handling. Reduced motion keeps the full hold duration and progressive reveal while removing body travel, morphing edges, pointer response and the commitment pulse. No send API, security policy, campaign behavior or global Send material changes are involved.

Every PIN entry field includes Show/Hide, including new PIN, confirmation, and verification for changes/removal or delivery. This reveals only the digits currently entered, never the stored PIN. Fields default to masked and hide again when focus leaves the field, verification starts, the value clears, or the modal closes. Leading zeroes are preserved throughout setup and verification.

Verification emails use `lib/email-verification-template.ts`: a narrow 540px white text layout with restrained NextGen branding, a strong purpose-specific headline, one explanatory paragraph, a large dark OTP, expiry, short security note and compact footer. There are no rounded cards, colored OTP panels, shadows, buttons, remote assets or custom fonts. Existing purposes (`delivery`, `send-pin-update`, `approval-email-verify`, `approval-email-change`, `settings-update`) map centrally to human-readable subjects, headlines and copy; delivery copy uses the actual message count and distinguishes creating drafts from sending. Codes remain out of subject lines, preserving the existing product behavior, while every subject explicitly says “verification code.” The visible code is a single contiguous selectable text node, spaced only with CSS. Plain text independently says “Your verification code is …” once and includes expiry and security instructions. Native Gmail Copy Code detection is controlled by Gmail and cannot be guaranteed by the template.

`renderVerificationEmail` accepts code, expiry, actual purpose, message count, delivery mode, optional workflow/email-type summary and brand/category/support-email/address overrides; dynamic HTML copy is escaped. The default footer is NextGen Solutions / EPR Consultancy / New Delhi, India. Tables and inline styles provide the base, with mobile spacing refinements and a 540px MSO fallback. Both HTML and meaningful UTF-8 plain text are sent. OTP delivery skips Gmail's default signature and its lookup; client sends and drafts retain their existing signatures. OTP generation, expiry, hashing, attempts, cooldowns and authorization are unchanged. `npm run verify:email-verification-template -- --render` checks purpose mappings, MIME transport with mocked Gmail, escapes, contiguous codes, signature isolation, 320/390px layouts and inline-only fallback, and writes fictional-code previews to `tmp/email-verification-template/`. These browser previews do not substitute for native Gmail Android/iOS or Outlook rendering checks; no live email is sent by the tests.

Commands:

- `npm run verify:email-delivery-security`: actual services and HTTP handlers against isolated atomic database/Gmail fixtures. Checks admin boundaries, settings restrictions, setup/change, hashes, expiry/resend/lockout/rates, exact batch/owner/policy binding, replay/concurrency, delivery recovery, unknown Gmail outcomes, quota pause/resume and safe audit.
- `npm run verify:email-delivery-security-ui`: production Settings/sidebar and authorization controls with isolated HTTP. Checks setup/change, sequential factors, PIN memory reset, error/resend/expiry recovery, hold cancellation/keyboard, StrictMode, search, dark/mobile and reduced motion. Captures live under `tmp/email-delivery-security-ui/`.
- `npm run verify:email-delivery-review`: the production tracker page, including repeated recipient additions, validation, signature preview, skipped/zero/500 clients, drafts, direct authorization, early-release hold and unchanged-campaign retry. Captures live under `tmp/email-delivery-review-tests/`.
- `npx tsc --noEmit`, lint and `npm run build` validate compilation and production routes.

Tests do not connect to production MongoDB or send real OTPs/client mail. Atomic database fixtures exercise the implemented conditional operations; they do not substitute for deployment validation of MongoDB indexes and real Gmail credentials. No deployment, environment-secret replacement or production-data mutation is included in this implementation.
